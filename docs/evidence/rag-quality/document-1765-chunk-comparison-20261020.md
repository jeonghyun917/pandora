# 문서 1765 청크 불일치 진단

## 실측과 방법

- 제품 기준: `e1c3d314` 이후 제품 변경 없음. 원본 SHA-256 `0f8cc5058d33f16d69ae558256086f07334c2480bca48a41ba2a6b5323c74893` 재확인.
- MariaDB `START TRANSACTION READ ONLY` 조회 `df2196`, JDBC read-only/rollback 대조 `faa2c8`, 원본 XML 문자 노드 전수 대조 `059dbe` exit 0. 비밀번호/쿠키/토큰의 브라우저 추출 없음.
- 실제 원본은 `Contents/section0.xml` 하나. 현 추출 결과 1개 섹션, chunkV4 raw 17개, quality retained 17개. HWPX의 pageNo는 이 추출기의 섹션 순번이며 물리 페이지 수로 해석하지 않는다.
- 원본 `t` 문자 노드(공백 제외, 비어 있지 않은 노드) 102개를 저장 전체/재생성 전체에 각각 대조: 양쪽 누락 0. 이는 문자 값 보존 검사이지 행 관계·순서·의미 동등성의 증명이 아니다.

## 원인 판정

두 추출 세대의 차이다. 과거 추출기는 `Contents/` 아래 모든 XML을 정렬해 텍스트화했고, 현재는 `Contents/section\\d+\\.xml`만 처리한다. 과거 코드(`82456329^`)가 헤더를 가상 page 1로 넣을 수 있고 실제 본문이 page 2로 밀리는 현상과 일치한다. 이후 표 행/셀/헤더 구조 보존 변경으로 평탄화된 두 큰 덩어리가 개별 행으로 나뉘었다. 정확한 과거 import 실행 SHA는 DB에 없어 특정 커밋에서 적재됐다고 단정하지 않는다.

따라서 `chunkCount` 차단은 올바르다. 같은 fileHash/chunkVersion=4라도 추출·분할 계약이 같다는 뜻이 아니며, 4→17 강제 매핑이나 개수 검증 완화는 금지한다. 문자 누락은 관측되지 않았지만 기존 구조는 원문 행 소유를 증명하지 못한다.

## 안전한 복구 방안과 실행 경계

1. 메타데이터-only backfill을 사용하지 않는다. 기존 4개/ID/임베딩/Q 포인트를 그대로 유지한다.
2. 원본 SHA와 문서 snapshot, 추출기/청킹 제품 SHA를 고정한 **문서 단위 비활성 후보**에 17개를 생성한다. 대상은 1765 하나이며 기존 활성 청크를 덮어쓰지 않는다.
3. 후보 검증: 원문 literal 전수 보존, 원본 좌표/병합셀/표 경계/중복행/계획변경 단서 보존, 타기관·잘못된 날짜·단서 삭제 음성 검사. 문자 노드 누락 0만으로 승격하지 않는다.
4. 새 ID의 임베딩·벡터/키워드 후보를 준비하고 DB-Q 개수·내용 지문을 대조한다. 외부 전송은 기존 승인 범위와 새 runtime/quota/network 확인 후에만 수행한다.
5. snapshot CAS와 원자적 활성 전환, 기존 검색 버전/벡터 보존을 갖춘 경로에서만 승격한다. 실패 주입으로 중간 DB/Q/색인 실패 시 기존 버전 유지 및 후보만 정리됨을 먼저 검증한다. 성공 후에도 rollback 가능한 이전 snapshot을 보관한다.

현재 `RagImportService.importFile(force=true,indexNow=false)`는 대안이 아니다. 기존 임베딩 supersede, 활성 청크 deactivate, 새 청크 insert와 keyword rebuild를 수행하므로 dry-run/비활성 후보가 아니다. 기존 관리 화면의 법령/행정규칙 재구축 후보 경로를 공식문서 복구에 임의 전용하지 않는다. 문서 단위 후보/승격/rollback 경로의 구현·검증이 필요한 후속 작업이며 이번 진단에서는 운영 데이터 변경을 실행하지 않았다.

호스트 공식 status `df2196`은 현재 8080/6333 리스너 없음과 stale app PID를 보고했다. 이번 읽기 전용 DB/원본 진단에는 영향 없으며 임의 기동/배포하지 않았다. 실제 복구 실행 전 공식 런타임 재확인이 필요하다. 예약은 PAUSED로 유지한다.
